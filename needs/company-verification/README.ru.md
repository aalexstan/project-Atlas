# Проверка контрагента

[English version](README.md)

> Какой API или источник выбрать для проверки контрагента?

Этот маршрут помогает перейти от задачи пользователя к текущим исследованиям Atlas по российским данным о компаниях и контрагентах. Он не заменяет закупку, юридическую проверку или живой тест.

## Определение задачи

Задача - определить, обогатить или проверить юридическое лицо или ИП перед onboarding, оплатой, закупкой, обогащением CRM, риск-мониторингом или построением внутренней data platform.

## Кому подходит маршрут

- Продуктовым командам, которым нужно автозаполнение реквизитов или карточка контрагента.
- Разработчикам, выбирающим API для CRM, ERP, onboarding или B2B-форм.
- Командам закупок, финансов, legal или безопасности, которые готовят shortlist.
- Data-командам, выбирающим между покупкой API и собственной registry warehouse.

## Сценарные маршруты

### Быстрое заполнение реквизитов, B2B-форма, CRM

Начните с [DaData](../../apis/dadata/README.ru.md), если задача - поиск компании, подсказки по компаниям, обогащение адресных или контактных данных и быстрая self-service интеграция для российского продукта.

Это не доказывает, что DaData является лучшим выбором для глубокого enterprise risk analysis. Текущая карточка Atlas описывает DaData как сильный вариант для ввода и обогащения данных, а не как полную замену due diligence.

### Корпоративная проверка, риск-контроль, мониторинг

Сформируйте shortlist из [Контур.Фокус API](../../apis/kontur-focus/README.ru.md) и [Seldon.Basis API](../../apis/seldon-basis/README.ru.md). Не объявляйте победителя до получения сопоставимых коммерческих предложений, SLA, технической документации, production limits, прав на данные и live test на одной выборке.

Используйте [сравнение API проверки контрагентов](../../comparisons/company-counterparty-data-russia/README.ru.md) и [procurement kit](../../procurement/counterparty-api-selection/README.ru.md), чтобы структурировать пилот.

### Связи, закупки, расширенный контекст

Оценивайте [Seldon.Basis API](../../apis/seldon-basis/README.ru.md), когда нужны связи, закупочный контекст, финансовые/судебные факторы, покрытие России/СНГ или выбор индивидуального набора методов.

Перед обязательствами проверьте цену каждого нужного метода, правила списания за вызовы, batch behavior и влияние частичных ошибок batch на стоимость или результат.

### Собственная полная база ЕГРЮЛ/ЕГРИП

Используйте маршрут [интеграции ФНС с ЕГРЮЛ/ЕГРИП](../../apis/fns-egrul-egrip-integration/README.ru.md), если организации нужна registry warehouse из первичного источника с контролем ETL.

Это FTP/XML data feed, а не обычный REST API. Нужны загрузка архивов, парсинг версионированного XML, применение daily deltas, хранение истории, мониторинг пропущенных файлов и собственная база или internal API. Стоимость доступа нельзя честно сравнивать без разработки, инфраструктуры, юридической проверки, поддержки, мониторинга и эксплуатации.

### Одна официальная выписка

Для одной официальной выписки веб-сервис ФНС - отдельный маршрут, отличающийся от выбора bulk API. Он может быть полезен для единичного доказательства, но это не bulk API, не полный registry feed и не готовый due-diligence продукт.

### 115-ФЗ и санкции

Не считайте, что стандартный API проверки контрагентов полностью решает AML, 115-ФЗ или sanctions screening. Специализированные compliance-продукты и юридические требования нужно оценивать отдельно. Текущее сравнение company-data API указывает, что Kontur.Compliance API следует оценивать отдельно для этого сценария.

## Ограничения текущего исследования

- В активных карточках и сравнении не использовались live credentials.
- Цены API Контур и Seldon требуют коммерческих предложений.
- SLA, хранение, redistribution, SaaS display и data-retention rights требуют письменного подтверждения.
- Полная стоимость ФНС сильно зависит от внутреннего ETL и эксплуатации.
- Нет benchmark, который доказывает превосходство на реальной пользовательской выборке.

## Вопросы перед закупкой

1. Какие поля обязательны для продукта или процесса?
2. Какой объём запросов, peak rate и batch size ожидаются?
3. Нужен мониторинг или только разовое обогащение?
4. Можно ли хранить, кэшировать, показывать клиентам или передавать ответы?
5. Сценарий внутренний, SaaS-facing, regulated или resale-oriented?
6. На каком правовом основании тестовая выборка отправляется поставщикам?
7. Какой трёхлетний TCO с учётом внедрения и эксплуатации?
