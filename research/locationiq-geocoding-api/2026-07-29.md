# LocationIQ Geocoding API Research Log — 2026-07-29

## Scope

Evaluate whether LocationIQ should become an active Atlas profile for address/geocoding selection.

Covered:

- Search / Forward Geocoding;
- Reverse Geocoding;
- Autocomplete;
- Nearby POI as a related capability;
- pricing, rate limits, authentication, caching and batch boundaries.

Out of scope:

- routing, maps, matrix, map matching and optimization APIs;
- live credentialed testing;
- legal advice on OpenStreetMap/ODbL, attribution, derived databases, SaaS or redistribution.

## Confirmed Facts

- LocationIQ documents separate APIs for Search / Forward Geocoding, Reverse Geocoding, Autocomplete, Nearby POI, routing and maps.
- Forward geocoding uses `/v1/search` and has US/EU endpoint examples.
- Reverse geocoding uses `/v1/reverse` and requires `key`, `lat` and `lon`.
- Autocomplete uses a separate `/v1/autocomplete` endpoint.
- API Reference documents access-token authentication and key-management restrictions.
- Public pricing lists a Free plan, paid plan examples, request allowances and per-second limits.
- Provider support says a single API request cannot contain a batch of addresses; each address is a separate request.
- No live testing, benchmark or contract review was performed.

## Provider-Reported Claims

- Enterprise plan has custom pricing, request rates, contracts and SLAs.
- API output can be stored forever; caching is limited by account status.
- Large batch processing may be arranged for a fee.
- Coverage and quality are worldwide/enterprise-grade according to provider positioning, but Atlas has not benchmarked it.

## Observations

- The Search/Reverse APIs are Nominatim-compatible in JSON/XML formats while LocationIQ-specific enhancements require JSON or `xmlv1.1`.
- LocationIQ is closer to Geoapify/OpenCage as a hosted commercial geocoding/autocomplete provider than to FIAS/GAR or DaData cleaning.
- Nearby POI is useful context but should not be treated as equivalent to 2GIS Places API or Yandex Organization Search without a separate place-search evaluation.

## Unknowns

- Exact enterprise SLA/support terms.
- Contract treatment of SaaS embedding, redistribution, resale, API proxying and model training.
- ODbL/attribution and derived-database obligations for the user's data flow.
- House-level precision, autocomplete relevance, latency and false-positive rate on target samples.
- Whether Maps Lite is usable for the intended geocoding workload or is maps-focused.
- Privacy/DPA terms for submitted addresses and coordinates.

## Contradictions and Cautions

- Public pricing/product cards can combine map and geocoding messaging; Atlas should confirm plan scope before procurement.
- Provider storage/caching help articles are useful but do not replace legal review.
- "Can store output forever" should not be promoted to unrestricted redistribution or model-training rights.

## Commercial Blockers

- Enterprise quote and SLA.
- Method-level scope by plan.
- Overage and persistent excess handling.
- Batch-fee model and evidence requirements for large offline jobs.

## Legal/Data-Rights Blockers

- Attribution and OpenStreetMap/ODbL treatment.
- Long-term storage versus cache of request-response pairs.
- Customer-facing display, SaaS embedding, redistribution and resale.
- Personal-data and privacy review for submitted addresses/coordinates.

## Live Testing Status

No live LocationIQ API request, benchmark, API-key use, batch job or UI test was performed.

## Profile Decision

Create an active reviewed profile for `apis/locationiq-geocoding-api/`.

Rationale: official LocationIQ sources provide product identity, endpoint boundaries, authentication, public pricing/rate limits, API reference, caching/batch guidance and enough scenario context for an Atlas reviewed profile.
