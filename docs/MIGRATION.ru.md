# Переход к API-first модели

[English version](MIGRATION.md)

## Почему нужна миграция

Текущий репозиторий объявляет Dataset главной сущностью, а API — способом доступа. Atlas возвращается к API-first продукту, сосредоточенному на выборе, сравнении и мониторинге.

Исследования наборов данных не потеряны. Они становятся вспомогательными доказательствами при оценке API.

## Правила

1. Не удалять полезные исторические исследования.
2. Не переносить всё одним непроверенным изменением.
3. Мигрировать материал при его использовании или повторной проверке.
4. Сохранять источники и происхождение.
5. Явно отмечать устаревшие и неопределённые сведения.
6. Не создавать несколько активных карточек одного API.

## Соответствие понятий

| Предыдущая сущность | Новая роль |
|---|---|
| Dataset | Информация о покрытии данных, поддерживающая карточку API |
| Provider | Общий контекст поставщика |
| Access method | Раздел технического доступа в карточке API |
| Relationship graph | Возможное производное представление в будущем |
| Catalog card | Кандидат на миграцию в карточку API |
| Research report | Доказательство или журнал исследования |
| Rating table | Отложено до появления публичной и проверенной методики |

## Постепенный процесс

1. Добавить новые корневые README и документы.
2. Создать `apis/`, `comparisons/` и `needs/` для новой работы.
3. Построить эталонную карточку DaData.
4. Перенести только старые карточки, нужные для первого сравнения.
5. Перемещать исторические материалы в `legacy/` только после проверки.

## Источник истины

Для новой работы:

- факты об API хранятся в карточках API;
- сравнительные выводы — в сравнениях;
- сырые заметки — в журналах исследований;
- существенные изменения продукта — в истории изменений.
